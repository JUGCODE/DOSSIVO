# PACIscan 与 DOSSIVO 对齐回复及实施补充

日期：2026-10-26  
发出方：DOSSIVO 实现侧，供 Claude 继续开发 paci-core 0.2 使用  
状态：DOSSIVO 侧推荐契约，待 Claude 在 core 0.2 交付中逐项确认。本文不修改 PACIscan 正式宪章，不表示双方已经确认接口，也不表示两套服务已经连通。

## 1. 接入决定与架构回复

继续沿用并修复 paci-core，保持 Claude 负责 PACIscan 通用核心、DOSSIVO 负责企业业务与服务端适配的分工。Record、Explore、Verify、Challenge 四项能力全部保留；AI Ledger 与 Jurisdiction Ledger 保持原名。DOSSIVO 不另写一套 PACI 内核。

对 `ALIGNMENT.md` 第 D 部分的回复如下。技术栈选择由实现侧承担，用户不需要再决定框架或数据库。

| 问题 | DOSSIVO 侧明确回复 |
| --- | --- |
| 当前前端与路由 | React 19.2.6；采用 Next 16.3.4 的路由约定；实际构建使用 Vinext 1.0.0-beta.5 与 Vite 8.0.13。这里不把 Next 路由约定等同于已部署完整 Node Next 服务。 |
| 当前服务端环境 | Cloudflare Workers，启用 `nodejs_compat`。浏览器调用 DOSSIVO 同源 API，由服务端完成身份、租户、权限和操作校验。 |
| 当前数据库 | Cloudflare D1，SQLite 数据模型；Drizzle ORM 0.45.2。新增 bridge 存储目前使用 D1 的参数化 SQL 与批量事务。R2 尚未启用。 |
| PACI 部署方式建议 | PACIscan 继续作为独立的 Node 22 + TypeScript 服务。第一阶段提供存储接口及 SQLite 事务持久化实现。内存 `Map` 可用于测试或缓存，不能作为持久化交付。 |
| 两者如何连接 | DOSSIVO 仅在服务端通过适配器调用经过认证的内部 HTTP 服务。浏览器只访问 DOSSIVO 同源 API，不直接访问 PACI 内部端点或持有其连接密钥。 |
| Workers 兼容性 | 本阶段先开发 HTTP 契约和持久化边界，不要求 Claude 把核心全部迁移到 Workers，也不要求先解决全部 `node:crypto` 差异。以后可在同一存储接口下增加 D1 等适配器，继续共用一套核心。 |

上述版本依据本仓库的 [package.json](../package.json) 与 [vite.config.ts](../vite.config.ts)。这是本次交付的实际配置快照，不是对这些依赖最新版本的声明。

建议的持久化边界是：PACI 自己的记录版本、账本事件、检查、授权、争议、幂等登记和必要日志状态进入 PACI 存储；DOSSIVO 的任务、档案准备快照、业务质疑及待发送请求留在 DOSSIVO D1。PACI 一次逻辑写入涉及的版本、事件及幂等登记应使用事务保证一致。跨服务不能假定存在一个共享数据库事务，应以稳定操作标识、待发送队列和可恢复回执连接。

## 2. 当前已经落地与尚未落地的边界

当前代码中的 [paci-bridge-core.js](../lib/paci-bridge-core.js)、[paci-bridge-store.js](../lib/paci-bridge-store.js)、[同源 API](../app/api/paci-bridge/route.ts) 和 [数据库表](../db/schema.ts) 已实现 DOSSIVO 侧准备流程：

- 按固定 `case_version` 保存私有档案快照，并保存本地内容摘要。
- 将登记、质疑、回应和撤回意图写入待发送队列，保存幂等键、命令摘要与目标版本。
- 对业务质疑追加 `OPENED`、`RESPONDED`、`WITHDRAWN` 历史，保留原快照关联。
- 查询与导出按登录用户的当前身份限定范围；导出前核对本地快照摘要。
- 当前只接受内置的合成演示流程；企业确认字段仍是企业确认，不会升级成独立第三方证明。

对应表为 `paci_dossier_snapshots`、`paci_bridge_requests`、`paci_bridge_challenges` 和 `paci_challenge_events`。它们是 DOSSIVO 的持久化准备记录，不是 PACI 账本的持久化实现。当前演示以登录用户 ID 作为租户边界，不能据此宣称多组织、多角色授权已经完成。

当前没有部署并连接 PACI HTTP 服务，没有经过验证的真实 CN 区域主机，也没有配置服务间连接密钥或回执验证链。所有 bridge 请求保持 `PENDING`；读取结果为 `connection: NOT_CONNECTED`；档案中 `paci_record_refs` 为空、`log_checkpoint` 为 null、`deployment_region` 为 `UNVERIFIED`。导出的 `proof_package` 为 null。没有 PACI 回执，就不显示“已登记”“已独立验证”或“已进入中国区透明日志”。

快照的本地 SHA-256 只用于检查这个 DOSSIVO 快照是否发生变化，不是已经公开登记的加盐承诺、独立见证或可信时间证明。后续适配器、发送任务和回执入库仍须开发；本文描述的内部 HTTP 边界是下一步实施契约，不是已有网络连接。

## 3. 对词汇对接 B1 至 B5 的回复

### B1 来源与派生关系

认可来源仅使用 `SELF_REPORTED`、`INSTRUMENTED`、`THIRD_PARTY_ATTESTED` 三个值。AI 生成或加工不是新的来源等级，使用 `DERIVED_FROM` 关系指向实际输入材料的确定版本。AI 输出仍须按实际产生与记录方式标明来源，不能因为经过模型处理就获得更高可信度。

认可将原 `authority_issued` 映射为 `THIRD_PARTY_ATTESTED` 加 `attestor_kind = AUTHORITY`；0.1 实际结构中的对应位置是 `attestor.kind`，最终字段名在 HTTP Schema 中明确，不另造两套含义。该类型表达出具者身份类别；来源签名是否得到核验、出具者是否真实、对当前问题有何效力，仍分别检查。不同机构名称也不自动证明独立控制关系。

`INSTRUMENTED` 应由获授权的实际采集路径产生，不能由浏览器填写一个枚举就升级。导入旧报告可以记录本次接收动作，不能补造旧报告生成时已经存在的采集授权、AI 执行或 PACI 历史。

### B2 声明评估与记录检查分开

认可 `claim_assessment` 专门表示声明与证据之间的评估，和单条记录的 `verification` 分开。DOSSIVO 已声明的评估值为 `SUPPORTED`、`SELF_DECLARED_ONLY`、`EXPIRED`、`CONTRADICTED`、`UNRESOLVED`、`OUTSIDE_SCOPE`。若上游使用小写形式，须在版本化协议中明确转换，不能默认为任意大小写均可。

`SUPPORTED` 不是法律合规证明；完整性检查成功也不直接意味着声明成立。声明评估必须固定声明、证据、关系、范围和规则版本，并说明限制及未解决的冲突。当前本地准备快照只显示 `UNRESOLVED`，不推定上游已经作出评估。

### B3 每项检查及显式失败

认可每项检查分别记录 `PASSED`、`FAILED`、`INCONCLUSIVE`，保留检查对象、范围、输入版本、方法、执行者及时间。缺材料、未执行、无法认证来源，不能被压成成功。

**建议在附件 B3 的派生展示标签中增加 `VERIFICATION_FAILED`，待 Claude 确认。** 目的是让已发生的检查失败直接可见，同时继续并列展示不同检查的结果。它与生命周期轴的 `FAILED` 分开：前者表示针对特定对象及范围的验证失败，后者表示行动执行失败。任何一种都不自动等于声明虚假或主体违法。

旧成功不得遮蔽当前失败；后来重新检查也应形成新记录并关联先前检查，保留失败历史。成功、失败或未知如何成为“当前结果”，应依据确定版本、输入摘要、检查范围、规则及检查器版本，不能把不同对象或不同时点的结果合并成单一可信徽章。

当前 DOSSIVO 的 `projectChecks()` 只是按版本展示检查事实的本地投影，返回 `PASSED / FAILED / INCONCLUSIVE / UNVERIFIED`；它不是 PACI 附件 B3 已经修订的证明，也没有产生 PACI 检查回执。正式映射以 core 0.2 契约为准。

### B4 有效性显示轴

认可 `CURRENT / EXPIRED / SUPERSEDED` 作为 DOSSIVO 的有效性显示轴，不塞入 PACI 附件 B 的其他轴。到期必须保留 `expiry_basis` 的来源、规则版本及适用范围。买家设置的到期要求不能显示成法律失效；新版本出现也不自动证明旧版本虚假。

现有 `evidence_versions.valid_from / valid_until` 是业务时效字段，`proof_links.expires_at` 是访问授权期限；二者不等同。缺少到期依据时显示待确定，不凭产品名称或固定天数补造。core 0.1 词汇还包含 `REVOKED`，正式 Schema 应保留并明确它表示记录撤销还是其他有效性变化；不得与访问授权撤销混为一谈。

### B5 建议的附件 B7 补充

认可增加检查执行信息，以下是建议写入 B7 或其引用技术规范的最小内容，尚未写入正式宪章：

| 信息 | 推荐契约与呈现要求 |
| --- | --- |
| 实际执行人 | 保留 `performed_by`、所属组织或服务身份、授权引用及控制关系；不能仅写 SYSTEM 就省去实际责任主体。 |
| 执行类别与环境 | 保留 `executor` 的 `SYSTEM / CUSTOMER_ENV / PLATFORM_OPERATOR / THIRD_PARTY`，同时记录实际执行环境标识、环境类别、运行组件版本及可验证的区域信息。类别标签不能替代实际部署证据。 |
| 实际可见材料 | 保留 `COMMITMENT_ONLY / SUMMARY / FULL_CONTENT`，并绑定实际看到的对象、版本、摘要和披露范围；只收到摘要或指纹的后台，不能显示为已阅读原件。 |
| 独立性及依据 | 保留独立性判断的依据、控制关系、利益冲突及复核人资格引用。无法确认时显式保留未知；不能为了满足一个布尔字段而猜测独立性，也不能把“第三方”名称当作独立性依据。 |
| 方法与版本 | 记录实际检查方法、检查器版本、规则集版本及输入集合摘要；规则或方法改变后不沿用旧结果。 |
| 时钟与时间依据 | 区分事件发生时间、系统接收时间和检查时间；分别记录 `SYSTEM_CLOCK / TRUSTED_TIMESTAMP / CLAIMED` 及依据。没有接入可信时间服务，不写 `TRUSTED_TIMESTAMP`。 |

这些字段由经过认证的服务端与执行环境提供并核验，不能直接采用浏览器自报的执行人、独立性或可见范围。

## 4. 对规则落地 C1 至 C5 的补充

### C1 要求来源与法律效力分别建模

认可法域账本收录相关要求，同时保留 `STATUTE`、`REGULATION`、`OFFICIAL_GUIDANCE`、`CONTRACT`、`BUYER_REQUIREMENT`、`AUDIT_METHOD`、`INTERNAL_POLICY` 的来源类别。买家要求、合同义务、审核方法和内部政策不能直接贴上附件 D 的法律禁止标签。

对“官方指引可以使用附件 D 分类”的表述补充如下：**`OFFICIAL_GUIDANCE` 不自动具有法源约束力。** 系统还需保存约束力判断、依据和适用范围。指引参与法律分析时，应区分它解释的法律依据与指引自身的效力；无法确认时保留不确定性，不能仅因出自官方就推出 `PROHIBITED` 或必须取得法定许可。`NO_RESTRICTION_IDENTIFIED` 必须带本次评估范围、假设、法源与规则版本，不得显示为无条件合法保证。

上述校验需要覆盖通用登记、更正和专用法域接口，不能只在某一个便捷函数中成立。

### C2 独立裁决与正常业务处理分别推进

同一主体运营 DOSSIVO 和 PACIscan 时，平台自检不能冒充独立第三方复核。涉及该运营者的争议，不由运营者给自己作出独立裁决。`UPHELD / REJECTED / PARTIALLY_UPHELD` 应由已确认资格、非当事方且独立于运营者的复核人作出；上诉使用不同的合格复核人。

没有独立复核人时，独立裁决保持待复核。但企业回复、补充材料、追加更正、业务撤回，以及质疑者按权限撤回质疑，均可以继续。业务“已回应”“已更正”“已撤回”不写成 PACI 已经裁决；质疑者撤回也不等于争议事实已经判定。各动作保留自己的权限、时间、目标版本和历史。

第一位独立复核人的任命可以后续完成，不拦住核心修复、持久化、接口和正常业务流程开发。

### C3 区域日志的逻辑隔离与真实部署分开

认可按区域分流日志的方向，但一个内存进程中的区域 `Map` 只证明逻辑隔离，不能证明物理驻留、跨区访问控制、模型处理、运维或备份均在 CN 区域。更不能据此推定跨境合规已经满足。

当前 DOSSIVO 与 PACI 没有经验证的真实 CN 接入路径，保持 `deployment_region: UNVERIFIED`。后续区域配置应由受控宿主管理；改区需要明确迁移流程，不能通过覆盖租户配置无声迁移历史或后续记录。只登记获准的最小记录，也不意味着摘要、关系或元数据天然不敏感。

独立见证与外部锚定未实现时，保留 `witnessed: false`、`anchored: false` 及能力说明；收到一个布尔值或运营者签名不能替代实际独立见证证据。

### C4 发送、收到与接受是不同事件

认可发送动作完成可记为 `EXECUTED`。接收方收到与接受，分别记录对应事件及接收方依据；不得由发送企业自行声称对方已经接受。确认必须绑定实际接收方、相关发送动作、材料版本和接受范围。DOSSIVO 的队列入库、HTTP 请求成功或 PACI 登记回执，都不代表业务接收方接受材料。

### C5 导入与时间保持诚实

认可不补造历史。历史报告日期通常是报告中所声明的时间，应按实际来源记录；系统接收日期是本次系统观察，不可替换报告发生日期。采集授权与事件时间需验证，不能把授权前的旧事件标为已经受控捕获。没有可信时间证据，不允许仅由参数请求升级为 `TRUSTED_TIMESTAMP`。

## 5. 现有 DOSSIVO 字段如何对接

| 现有字段或对象 | 目前含义 | 与 PACI 对接的边界 |
| --- | --- | --- |
| `facts[].source_label` | 面向用户的资料来源文字 | 不是 PACI 来源枚举；须另行保留规范化 `source` 及具体来源引用。 |
| `confirmed_by_company` | 企业确认该业务事实 | 不自动成为 `THIRD_PARTY_ATTESTED`、`EVIDENCE_CORROBORATED` 或独立复核。 |

| 档案 `verification`、`checks` | 当前为 `UNVERIFIED`、空数组 | 本地内容摘要检查不能当成 PACI 全面验证；逐项回执到达后分别呈现。 |
| `outcome_cases.status`、步骤状态 | DOSSIVO 业务进度 | 不复用为 PACI 生命周期、验证或争议结论。 |

| `case_version` | DOSSIVO 任务快照版本 | 与档案内的 `client_version`、PACI `record_id + version` 分别保存并建立映射，不假定数值相等。 |
| `agent_runs` | DOSSIVO 本地运行记录容器 | 只有实际发生且满足授权与输入输出记录要求的 AI 执行才能写入 AI Ledger；合成演示或确定性流程不补造模型运行。 |
| Link1 / Link2 | 分层披露的业务入口 | 摘要与原件资源分别授权；版本、范围、到期和撤销必须真正作用于可访问资源。旧授权不自动覆盖新版本。 |

## 6. 六组能力的服务契约映射

下表是推荐的服务能力映射。所列 core 方法用于定位 0.1 已有能力，不表示 HTTP 路由已存在，也不直接认可其当前实现已经满足全部边界。路由、请求与响应 Schema 由 Claude 随 core 0.2 确认。

| 六组能力 | DOSSIVO 侧责任与当前状态 | PACI 服务侧对应能力 | 必须返回或保留的依据 |
| --- | --- | --- | --- |
| 1. 材料与记录登记、更正 | 当前 `prepare_registration` 保存固定快照并入队；后续适配器提交获准的最小记录及更正关系 | `registerRecord`、`amendRecord` | 操作回执、实际 `record_id + version`、内容承诺/摘要、前序版本或更正引用；不能以最新版本替代指定版本。 |
| 2. 行动与两类账本 | DOSSIVO 提供实际执行的授权、输入、工具、模型、输出与人工纠正；法域分析另带来源、假设与规则版本。目前未转发 | `recordAiAction`、`recordJurisdiction` | 行动记录身份、确定输入/输出引用、实际来源及时间；AI Ledger 和 Jurisdiction Ledger 的语义分别校验。 |
| 3. 检查与声明评估 | 仅服务端请求；先固定输入集合、版本、可见范围和授权。目前没有 PACI 检查回执 | `runCheck`，声明评估另走 `evaluate` | 每项检查结果及 B7 信息；评估另返回 `claim_assessment`、理由、范围和证据引用。禁止不经授权检查或评估不可读记录。 |
| 4. 授权查询与历史 | 当前只读取 DOSSIVO 本地准备数据；后续每次查询、重试、缓存命中和导出重新鉴权 | `getRecord`、`history`、授权授予/撤销接口 | 对本次权限投影后的确定版本和历史；授权引用、有效期、实际披露范围；不得恢复已删除正文。 |
| 5. 质疑与回应 | 当前本地 `open_challenge / record_response / withdraw_challenge` 追加历史并入队；没有 PACI 争议状态 | `openChallenge`、`respondChallenge`、`withdrawChallenge`、`getChallenge`；独立裁决和上诉另受控 | 固定被质疑版本、参与者可访问的回应及处理历史、真实争议状态；登记回执未到达前不得虚构目标 PACI 记录。 |
| 6. 导出与核验 | 当前只导出私有 DOSSIVO 准备清单与本地摘要，`proof_package: null` | `exportProofPackage` 及独立核验器 | 严格绑定身份、版本、披露材料、承诺与证明范围；明确正确公钥、见证、锚定和日志一致性的实际能力。 |

## 7. 请求与回执必须固定的版本关系

内部 HTTP 协议应版本化。以下是 core 0.2 推荐验收要求，不声称当前 DOSSIVO 表已经包含全部字段。

1. **操作身份。** 请求携带稳定 `operation_id`、租户范围内的 `idempotency_key`、协议版本及请求摘要。重试复用原标识；同键不同内容返回冲突。身份、租户及授权范围由 DOSSIVO 服务端和 PACI 服务端共同校验，不信任浏览器自报。摘要须明确算法与规范化版本。
2. **业务版本与记录版本。** 保存 `dossier_id`、DOSSIVO `case_version`、各项 `client_record_ref + client_version`，以及回执返回的 PACI `record_id + version`。更正携带预期前序版本；并发冲突不得静默覆盖。
3. **输入绑定。** 每次检查、评估及导出列出实际使用的声明、根证据、关系和披露对象的确定版本与摘要。引用不能在执行时悄悄解析为 latest。当前 `scope.ruleSet` 是业务文字标签，不能冒充机器可核验的规则版本。
4. **规则与检查器绑定。** 检查和评估回执至少固定规则集标识及版本、检查器标识及版本、方法与配置版本、检查范围、输入集合摘要以及 B7 执行信息。规则未知或材料不可见时，按实际情况返回未执行或无法判断，不能补全为成功。
5. **接收与验证回执。** DOSSIVO 先核对服务身份、操作标识、目标版本和摘要，再保存回执及本地到达时间。若回执声称有签名、检查点、见证或锚定，必须验证对应证据，不能只读取状态字段。登记回执与检查回执分开；登记成功不自动产生验证成功。
6. **失联与恢复。** 超时或回执丢失保持待同步/待确认，并按原操作标识向 PACI 查询或重试。不能重新生成操作制造重复登记，也不能用旧版本回执给新快照点亮成功状态。PACI 重启后应可从持久化存储恢复相同操作结果，并按调用者当前权限重新投影。
7. **披露与持久化。** 对端只接收获准的材料范围；原件、摘要和承诺分别处理。回执、检查及业务状态的更新须具备事务一致性或明确可恢复流程。未实际收到的字段继续为空；准备清单中的摘要不自动进入公共日志。
